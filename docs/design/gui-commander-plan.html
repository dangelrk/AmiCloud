AmiCloud — Plan: GUI-Dateimanager (Commander)

Zwei-Panel-Dateimanager im Stil von Midnight/Total Commander als grafisches Frontend über dem bestehenden Client-Kern — PC mit Qt 6 Widgets, Amiga mit MUI. Betrifft ausschließlich client/; Server und Handler bleiben unangetastet.

Status

v1 (2026-07-05): Erstfassung. Grundsatzentscheidungen (Toolkit-Wahl, Panel-Konzept, Phasenreihenfolge) sind getroffen, siehe Abschnitt 2 und 10.

Umsetzung (2026-07-05): Phase 0 (Hook-Schicht ui_hooks.c, Fortschritt+Abbruch in http_download/neues http_upload, Panel-Abstraktion panel.c/h) ist implementiert und gegen CLI/Shell regressionsgetestet (scripts/test_api.sh, byte-identisches Konsolenverhalten). Phase 1 (client/gui_qt/, Qt 6) ist implementiert, gebaut und lauffähig getestet (startet, laedt Panels, keine Laufzeitfehler) — volle interaktive Bedienung konnte in dieser Umgebung mangels Bildschirmzugriff (Screen-Recording/Accessibility) nicht visuell verifiziert werden. Phase 2 (client/gui_amiga/, MUI 3.8) ist geschrieben, aber unverifiziert — keine VBCC/MUI-Toolchain in dieser Umgebung verfügbar, siehe Warnhinweis in gui_amiga/gui.h; benötigt einen nativen Amiga-Build-Durchlauf. Phasen 3–4 (Komfortfunktionen, Politur/Paketierung) sind noch nicht begonnen.

1. Ziel & Ausgangslage

Neben CLI (amicloud) und interaktiver Shell (amicloud-shell) soll ein drittes Frontend entstehen: ein grafischer Zwei-Panel-Dateimanager (Arbeitstitel AmiCloud Commander, Binary amicloud-commander). Vorbild sind Midnight Commander / Total Commander / DirWork: zwei Dateilisten nebeneinander, Funktionstasten für Kopieren/Verschieben/Löschen, Statuszeile.

Die Ausgangslage ist günstig: Der Client ist bereits sauber geschichtet. cmd.c liefert mit cmd_list_raw() strukturierte Verzeichnislisten (AcEntry), localfs_* abstrahiert das lokale Dateisystem plattformneutral (LocalDirEntry), http_pc.c/http_amiga.c kapseln den Transport, pattern_* die Wildcards, config.c die Konfiguration. Das GUI setzt auf denselben Kern auf — der einzige echte Umbau ist eine dünne Callback-Schicht (Phase 0), CLI und Shell laufen unverändert weiter.

2. Toolkit-Entscheidungen

2.1 Amiga: MUI — nicht GadTools

KriteriumGadToolsMUI 3.8
Listen mit Spaltennein (nur einspaltige ListView)ja (MUIA_List_Format + Display-Hook)
Multiselectpraktisch nichteingebaut (MUIA_Listview_MultiSelect)
Font-sensitiv / Resizemanuelles LayoutLayout-Engine gratis
Tastaturnavigationmanuelleingebaut
Abhängigkeitim ROM (V37+)muimaster.library (Standard bei 3.x-Nutzern)

Für einen Commander ist die GadTools-ListView disqualifiziert. Entscheidung: MUI 3.8, bewusst nur eingebaute Klassen (Application/Window/Group/Listview/List/Text/String/Gauge) — kein NList-Zwang, damit die einzige Abhängigkeit die muimaster.library bleibt. NList ist ein optionales Upgrade in Phase 4. Build wie gehabt mit VBCC (Makefile.amiga), MUI-SDK-Header zusätzlich.

2.2 PC: Qt 6 Widgets — nicht QML

QTableView + eigenes QAbstractTableModel ist genau das Werkzeug für Dateipanels; Widgets binden den C-Kern trivial per extern "C" an. QML brächte für diese Art UI nichts außer Deployment-Gewicht. Build per CMake (Qt-üblich); die bestehenden Makefiles bleiben für CLI/Shell zuständig.

3.1 Panels

  • Jedes Panel ist umschaltbar Local ↔ Cloud (Total-Commander-Stil), nicht fix „links lokal, rechts remote“. Beide Quellen liefern schon identisch geformte Einträge (LocalDirEntry bzw. AcEntry: Name / is_dir / size / modified) — sie werden hinter einer gemeinsamen Panel-Abstraktion vereinheitlicht (Abschnitt 5.4).
  • Spalten: Name, Größe, Datum. Sortierung Name/Größe/Datum, Verzeichnisse immer zuerst, ..-Eintrag immer ganz oben.
  • Startzustand: links Local (CWD), rechts Cloud (/ bzw. basepath) — wie das Banner der Shell.

Grundregel: keine C++-Kontamination des Kerns

Der Kern bleibt C89-nah und VBCC-kompatibel. Die Qt-Seite kapselt ihn ausschließlich über extern "C"-Includes. Alles, was beide GUIs brauchen, kommt als reines C in panel.c — nichts davon darf Qt- oder MUI-Typen kennen.

5. Phase 0 — Kern GUI-fähig machen NEU

Der einzige echte Umbau; alles Weitere setzt nur oben drauf. CLI und Shell dürfen sich dabei nicht verändern.

5.1 Callback-Schicht ui_hooks.h

cmd.c druckt heute per printf/fprintf(stderr), shell.c fragt per confirm() auf stdin. Neue globale Hook-Struktur mit Funktionszeigern: 

typedef struct {
    void (*notify)(int level, const char *msg);          /* Info/Fehler        */
    int  (*confirm)(const char *msg);                    /* 1=ja, 0=nein       */
    int  (*progress)(long done, long total,              /* 0 = abbrechen      */
                     const char *name);
} UiHooks;
void ui_set_hooks(const UiHooks *h);   /* NULL = Konsolen-Default */

Default-Implementierung = heutiges Konsolenverhalten. Die fprintf/printf-Stellen in cmd.c werden auf notify() umgestellt, confirm() aus shell.c wandert hinter die Hook.

5.2 Fortschritt + Abbruch im HTTP-Layer

  • http_download() streamt bereits in eine FILE* — dort pro Chunk den progress-Hook rufen. PC: libcurl CURLOPT_XFERINFOFUNCTION; Amiga: http_amiga.c ist handgestrickt, Aufruf direkt in der recv-Schleife.
  • Rückgabe 0 des Hooks bricht den Transfer sauber ab (curl: Abort-Return; Amiga: Verbindung schließen, angefangene Zieldatei löschen).

5.3 Upload-Streaming (Amiga-kritisch)

cmd_put() lädt heute die ganze Datei per malloc in den Speicher (cmd.c:367) — auf einem 8-MB-Amiga ein Showstopper für größere Dateien. Neue Funktion http_upload(url, auth, FILE *fp, long fsize, ...) mit Chunk-Read + Progress-Hook. PC: libcurl CURLOPT_READFUNCTION; Amiga: http_amiga.c sendet ohnehin schleifenweise, statt aus dem Puffer eben aus der Datei lesen. cmd_put() intern umstellen, Signatur bleibt.

5.4 Panel-Abstraktion panel.c/h

  • Vereinheitlichter Eintrag (Name, is_dir, size, modified, mark-Flag) + Quelle PANEL_LOCAL/PANEL_CLOUD.
  • panel_read(src, path) → Eintragsliste (delegiert an localfs_opendir-Familie bzw. cmd_list_raw).
  • Sortierung (Name/Größe/Datum, Verzeichnisse zuerst), Markierungsverwaltung, Summen für die Statuszeile.
  • Pfadnavigation: remote_resolve()/path_push/path_pop wandern aus shell.c in ein gemeinsames Modul (z. B. paths.c oder direkt panel.c), ebenso shell_get_dir/shell_put_dir für die rekursiven Fälle — shell.c ruft sie danach von dort.

6. Phase 1 — Qt-Client MVP client/gui_qt/

  1. Start & Verbindung: AcConfig aus ~/.amicloudrc laden (vorhandener Loader); Connect-Dialog nur bei fehlender/unvollständiger Config. cmd_status() als Login-Test, Serverversion + TLS-Status in die Statuszeile (wie das Shell-Banner).
  2. Panels: zwei panelwidget-Instanzen (QTableView + Model über panel.h), Local/Cloud-Umschalter als ComboBox im Panel-Kopf, Pfadanzeige, Sortierung per Spaltenklick, Multiselect, Tastenbelegung aus Abschnitt 3.2.
  3. Operationen: F3/F5/F6/F7/F8 gemäß Matrix. Alle Netz-Operationen laufen in einem Worker-QThread (der Kern ist blocking); Progress-Hook → Qt-Signal → Fortschrittsdialog mit Abbrechen-Button (setzt das Cancel-Flag, das der Hook zurückgibt). confirm-Hook → QMessageBox, in den UI-Thread marshalled (QMetaObject::invokeMethod, blocking).
  4. Nach jeder Operation: betroffene Panels neu laden, Markierungen der erfolgreich verarbeiteten Einträge löschen.

7. Phase 2 — Amiga-MUI-Client MVP client/gui_amiga/

  1. Fensteraufbau (gui.c): ApplicationObject → WindowObject → HGroup mit zwei Panel-Gruppen (je: Umschalt-Cycle + Pfad-Text + Listview) + Button-Leiste (F-Tasten-Äquivalente) + Statuszeile. Spalten per MUIA_List_Format "BAR,BAR P=\33r," mit Display-Hook, Sortierung per Compare-Hook (panel_mui.c).
  2. Feature-Set identisch zu Phase 1 (gleiche Panel-Abstraktion, gleiche Hooks).
  3. Nebenläufigkeit pragmatisch: v1 synchron mit Busy-Pointer (MUIA_Application_Sleep) + kleinem Progress-Fenster mit Abbrechen-Button; der progress-Hook pollt zwischen den Chunks die GUI-Events (DoMethod(app, MUIM_Application_NewInput, ...)) — responsives Abbrechen ohne Task-Kommunikation. Falls das später nicht genügt: das Zwei-Prozess-Muster aus handler/ (exec-Messages, privater Reply-Port) ist im Projekt erprobt → Phase 4.
  4. Amiga-Anstand: $VER-String, Icon (.info), Menüleiste (Projekt/Über/Beenden), Config aus ENV:amicloud.cfg wie gehabt.
  5. Entwicklung: Syntaxprüfung auf dem PC wie gewohnt (clang -fsyntax-only -D_NO_INLINE -DAMIGA -DPLATFORM_AMIGA -IInclude_H ..., MUI-Header ergänzen), Nativ-Build und Test auf dem Amiga.

8. Phase 3 — Komfortfunktionen (beide Plattformen)

  • Rekursives Kopieren/Löschen mit Gesamt-Fortschritt (Dateien vorab zählen: Cloud via cmd_list_raw-Walk, lokal via localfs_opendir-Walk).
  • Überschreib-Nachfrage mit „Ja / Nein / Alle / Keine / Abbrechen“ (Erweiterung der confirm-Hook um einen Antwort-Enum).
  • Wildcard-Markierung (*-Dialog → pattern_match), Markierungs-Invertierung.
  • Inline-Umbenennen (Qt: Edit-Delegate; MUI: String-Gadget-Dialog).
  • Statuszeile: Anzahl + Gesamtgröße markierter Einträge.
  • Qt: Drag & Drop zwischen den Panels und aus dem System-Dateimanager; Kontextmenüs; Einstellungsdialog (schreibt ~/.amicloudrc).
  • Amiga: AppWindow (Icons aufs Fenster ziehen = Upload ins aktive Cloud-Panel); Panel-Verlauf.

9. Phase 4 — Politur & Paketierung

  • Qt: Programm-Icon, Dark-Mode-Check, Pakete für Windows/macOS/Linux (analog zum Makefile-Trio des CLI).
  • Amiga: optionaler Async-Worker nach dem Handler-Muster (falls synchrone Transfers in der Praxis stören); NList als optionales Listen-Upgrade; LhA-Archiv mit Installer-Skript + Aminet-Readme.
  • README-Abschnitt + Screenshots.

10. Entscheidungen & Risiken

  • MUI statt GadTools — GadTools-ListView kann weder Spalten noch Multiselect (Abschnitt 2.1).
  • Qt 6 Widgets statt QML — Tabellen-UI + triviale C-Anbindung (Abschnitt 2.2).
  • Panels frei umschaltbar Local↔Cloud statt fixer Zuordnung.
  • Qt vor MUI — die Phase-0-Callback-Schicht lässt sich auf dem PC schnell validieren, bevor die zähere Amiga-Runde beginnt.
  • Kern bleibt reines C, VBCC-kompatibel; GUIs sind reine Konsumenten.

Bewusste Auslassungen in v1

  • Cloud→Cloud-Kopie: serverseitig nicht vorhanden — ausgegraut; ggf. später API-Action copy (separates Server-Thema).
  • Kein Datei-Betrachter (F3-View): F3 ist Info; ein Viewer wäre besonders auf dem Amiga ein eigenes Projekt.
  • Amiga v1 synchron: Busy-Pointer + Abbruch-Polling statt Worker-Task — bewusster Einfachheits-Trade-off, Upgrade-Pfad existiert (Handler-Muster).

12. Testplan

  • Phase-0-Regression: CLI + Shell nach dem Hook-Umbau gegen den lokalen Testserver (php -S 127.0.0.1:8180 + scripts/test_api.sh-Setup) — Verhalten byte-identisch.
  • Upload-Streaming: große Datei (> verfügbarer RAM auf dem Amiga-Testgerät) hochladen.
  • Qt: Kopieren/Verschieben/Löschen in allen Richtungen der Matrix, Abbruch mitten im Transfer (halbe Zieldatei darf nicht liegen bleiben), Überschreib-Dialoge, Sonderzeichen/Umlaute in Namen.
  • Amiga nativ: gleiche Fälle; zusätzlich Abbruch-Reaktionszeit beim Chunk-Polling, RAM-Verbrauch, Verhalten bei Verbindungsabbruch (Roadshow offline).
  • Beide: Panel Local↔Cloud umschalten während markierte Einträge existieren; leere Verzeichnisse; sehr lange Namen/Pfade (AC_MAX_PATH).
