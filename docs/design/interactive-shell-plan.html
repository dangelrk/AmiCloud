1. Ziel & Scope

Aktuell startet amicloud für jede Aktion neu (Prozessstart → HTTP-Verbindung → Aktion → Exit). Für mehrere Operationen in Folge (z. B. mehrere get/put im selben Verzeichnis) soll ein neuer Modus amicloud shell eine interaktive REPL öffnen: einmal verbinden, dann beliebig viele Befehle eingeben, bis quit/exit.

  • Betroffen: nur client/, optional kleine, klar umgrenzte Erweiterungen in server/ (für rekursives Löschen und eine Versions-/Status-Auskunft).
  • Nicht betroffen: handler/ (bleibt wie er ist, auch wenn er nicht läuft), bestehende Makefiles werden nur um neue Quelldateien ergänzt — keine Flag-/Toolchain-Änderungen.
  • Plattform-Pflicht: AmigaOS 3.x (VBCC), macOS, Linux, Windows — exakt die Plattformen, auf denen client heute schon baut.
  • Syntax-Anspruch: jede Plattform soll sich „zuhause“ fühlen (Amiga-Wortkommandos, PC/Unix-Kurzflags) — aber alle Schreibweisen funktionieren auf jeder Plattform, siehe Abschnitt 8.
  • Referenzen bei Bedarf: netinclude/, include/, Include_H/ für Amiga-Signaturen (dos.library für Verzeichnis-/CWD-Operationen).

Bestehende Bausteine werden wiederverwendet, nicht verändert:

Neu hinzu kommen:

Der Grund für das eigene localfs-Modul: opendir/readdir/chdir existieren so auf AmigaOS/VBCC nicht (dort läuft alles über dos.library-Locks), während PC/Mac/Win POSIX-dirent.h bzw. MinGW-Äquivalente nutzen können. Genau dieses Muster gibt es im Projekt schon für HTTP (http_pc.c vs. http_amiga.c) — die Shell übernimmt es 1:1 für Dateisystemzugriffe.

3. Start & Optionen

Die Shell wird wie jedes andere Kommando aufgerufen und akzeptiert dieselben Optionen wie client heute:

amicloud [-s server] [-u user] [-p pass] [-d basepath] [-c cfgfile] [-k] [-v] shell

Konfiguration wird exakt wie bisher geladen (config_load → config_merge), inklusive Config-Datei-Fallback (~/.amicloudrc / ENV:amicloud.cfg). Fehlt Server/User/Passwort, bricht der Start wie gewohnt mit Usage-Hinweis ab — die Shell wird also nie ohne gültige Zugangsdaten geöffnet.

Hinweis: Die Startoptionen (-s/-u/-p/…) bleiben bewusst bei der bestehenden Kurzflag-Syntax — sie werden vom Betriebssystem-Kommandozeilen-Parser vor dem Shell-Start verarbeitet (identisch zu allen anderen Kommandos wie list/get). Die in Abschnitt 8 beschriebene Mehrfach-Syntax betrifft ausschließlich Befehle innerhalb der Shell.

4. Session-State: Remote-/Local-CWD

Wichtigste Design-Entscheidung, um cmd.c unverändert wiederverwenden zu können:

Die Shell hält eine Kopie der geladenen AcConfig (base_cfg) plus einen zusätzlichen String remote_cwd[AC_MAX_PATH], initialisiert mit base_cfg.basepath.

Vor jedem Remote-Befehl wird eine flache Kopie eff = base_cfg erzeugt, deren basepath auf remote_cwd gesetzt wird — anschließend ruft die Shell cmd_list()/cmd_get()/… unverändert mit &eff auf. So bleibt cmd.c komplett unangetastet.

Analog für lokal: local_cwd wird beim Start per localfs_getcwd() ermittelt (Startverzeichnis des Prozesses) und über lcd verändert.

Pfad-Normalisierung: Der Server lehnt .. im Pfad mit HTTP 400 ab (sanitizePath() in server/includes/FileStore.php). cd muss alle in Abschnitt 8 definierten Kurzsymbole (Parent-/Root-Marker, gleich welcher Schreibweise) deshalb client-seitig auf remote_cwd auflösen, bevor der resultierende, saubere /-Pfad an den Server geschickt wird. Danach wird das Ziel per info-Aufruf verifiziert (muss existieren und type=dir sein) — erst dann wird remote_cwd aktualisiert. Schlägt die Prüfung fehl, bleibt der alte Stand erhalten und es gibt eine Fehlermeldung, kein Shell-Abbruch.

5. Eingabeschleife & Parsing

  • Zeilenweises Lesen über fgets(stdin) — bewusst kein readline/libedit, da das auf AmigaOS/VBCC nicht portabel verfügbar ist. Grundlegende Zeilenbearbeitung (Backspace, Cursor) liefert die jeweilige Konsole (CLI-Shell auf Amiga, Terminal auf Unix, Konsole auf Windows) ohnehin bereits.
  • Ein einfacher, quotation-fähiger Tokenizer (Leerzeichen trennen Argumente, "..." erlaubt Pfade/Dateinamen mit Leerzeichen — auf Amiga durchaus üblich).
  • Jedes Token wird zusätzlich durch den in Abschnitt 8 beschriebenen Flag-Erkenner geprüft (kurz/lang/Amiga-Wort), bevor der Rest als Positions-Argument (Pfad) gewertet wird.
  • Leere Zeile → erneut Prompt, kein Fehler.
  • Kommando nicht erkannt → Fehlermeldung + Hinweis auf help, Shell läuft weiter.
  • EOF (Ctrl-D / Ctrl-Z) wird wie quit behandelt.

6. Start-Banner & Prompt

Direkt nach Verbindungsaufbau, vor dem ersten Prompt, gibt die Shell aus:

  • Client-Version (AC_VERSION) und Plattform (Amiga/macOS/Linux/Windows)
  • Server-URL, Benutzername, aktives Remote-Basisverzeichnis
  • Verbindungsstatus: ein leichter Check-Request beim Start (neue status-Action, siehe Abschnitt 10) — Erfolg zeigt Server-Version, Fehlschlag zeigt eine Warnung, beendet die Shell aber nicht (lokale Befehle wie lcd/lpwd/help bleiben nutzbar, Remote-Befehle liefern dann einfach ihre gewohnte Fehlermeldung).
  • TLS-Verify-Modus (an/aus, relevant falls -k gesetzt war)

6.1 Prompt-Format — entschieden

Kein amicloud:-Präfix vor dem Pfad — der Prompt ist schlicht der aktuelle Remote-Pfad, dargestellt mit dem plattform-nativen Root-Symbol aus Abschnitt 8.2 (: auf Amiga, / auf macOS/Linux, \ auf Windows) und entsprechend nativen Trennzeichen für die Unterverzeichnisse. Nur der Remote-Pfad wird angezeigt (kein lokaler Pfad im Prompt — dafür gibt es lpwd).

PlattformRoot (Beispiel)In Unterordner „sub/dir“
Amiga:> :sub/dir>
macOS / Linux/> /sub/dir>
Windows\> \sub\dir>

Intern bleibt remote_cwd immer ein kanonischer /-Pfad (so wie die API ihn erwartet, Abschnitt 4) — die Umwandlung in die native Anzeigeform passiert nur für Prompt und pwd-Ausgabe, ist also rein kosmetisch und hat keinen Einfluss auf das Wire-Format zum Server. 

AmiCloud Shell v0.1 (macOS)
Server   : https://amicloud.example.com  (Server v0.2, TLS ok)
User     : bob
Remote   : /
Local    : /Users/bob/Downloads
Type 'help' for a list of commands, 'quit' to exit.
/>

Direkt nach dem Start entspricht der aktuelle Ordner der Basis (remote_cwd == basepath, per Default /) — ein ls ohne Pfadangabe zeigt also sofort die Wurzel, ganz ohne vorheriges cd.

8. Plattform-angepasste Syntax

Grundidee: jede Schreibweise funktioniert auf jeder Plattform — ein Amiga-Nutzer, der aus Gewohnheit RECURSIVE tippt, bekommt auf dem Mac dasselbe Ergebnis wie mit -r; ein PC/Linux-Nutzer, der versehentlich ein AmigaDOS-Keyword tippt, wird nicht mit „unknown command“ abgewiesen. Nur an einer Stelle gibt es einen echten, nicht auflösbaren Bedeutungskonflikt (/ für Root vs. Parent) — dort gewinnt die native Konvention der Plattform, auf der der Client gerade läuft.

8.1 Flags (Rekursiv, Force, …)

Jede Flag wird in drei gleichwertigen Schreibweisen erkannt, überall gleichzeitig aktiv:

BedeutungKurz (PC/Unix-Stil)Lang (GNU-Stil)Amiga-Keyword (case-insensitiv)
Rekursiv-r--recursiveRECURSIVE / recursive / All
Erzwingen / ohne Nachfrage-f--forceFORCE / force

Ein gemeinsamer Helper (etwa flag_match(token, "-r", "--recursive", "RECURSIVE"), case-insensitiv nur für die Keyword-Form — Amiga-ReadArgs-Keywords sind traditionell nicht case-sensitiv, kurze/lange Flags bleiben klassisch kleingeschrieben) prüft jedes Token, bevor es als Pfad-Argument gilt. Reihenfolge der Flags relativ zu den Positions-Argumenten ist frei (del -r -f /ordner, del /ordner FORCE RECURSIVE, del -f /ordner --recursive — alle drei gleichwertig).

8.2 cd/lcd-Kurzsymbole

BedeutungEingabeGültigkeit
Ein Verzeichnis hoch (Parent) ..überall (universeller Alias, kollisionsfrei)
/nur wenn Client auf AmigaOS läuft — native Amiga-Konvention
Zur Wurzel (Root) :überall (universeller Alias, kollisionsfrei — bloßes „:“ hat sonst keine Bedeutung)
\überall (Windows-native Schreibweise, kollisionsfrei auf allen anderen Plattformen)
/nur wenn Client NICHT auf AmigaOS läuft (macOS/Linux/Windows) — native Unix-/Pfadkonvention
Zurück zum konfigurierten Basisverzeichniscd/lcd ohne Argumentüberall (unverändert wie ursprünglich geplant)

Der einzige echte Konflikt: /

/ bedeutet auf AmigaOS „eine Ebene hoch“ (z. B. /foo = Geschwisterverzeichnis foo), auf macOS/Linux/Windows dagegen „absolute Wurzel“. Beide Bedeutungen gleichzeitig zuzulassen ist unmöglich — deshalb wird / exakt wie von dir beschrieben plattform-nativ zur Compile-/Laufzeit interpretiert (#ifdef PLATFORM_AMIGA in shell.c, gleiches Muster wie beim bestehenden http_pc.c/http_amiga.c-Split). Alle anderen Symbole (.., :, \) sind eindeutig und deshalb überall gleichzeitig aktiv.

Diese Kurzsymbol-Auflösung gilt für beide Befehle, cd (remote, wird zu einem saubern /-Pfad normalisiert bevor er an die API geht, siehe Abschnitt 4) und lcd (lokal, wird 1:1 an localfs_chdir() auf der jeweiligen Plattform durchgereicht — dort greift ohnehin die native Interpretation des zugrunde liegenden Dateisystems).

9. Rekursive Operationen im Detail

9.1 put -r (Ordner hochladen)

  1. Lokalen Verzeichnisbaum ab <lokal> traversieren (localfs-Modul, Tiefensuche).
  2. Für jedes gefundene Unterverzeichnis: mkdir-Action aufrufen (HTTP 409 „existiert bereits“ wird ignoriert, ist kein Fehler).
  3. Für jede gefundene Datei: bestehende Upload-Logik aus cmd_put wiederverwenden.
  4. Fortschrittsausgabe pro Datei (Pfad + ok/Fehler); ein Fehler bricht nicht den ganzen Lauf ab, wird aber am Ende als Zusammenfassung („12 Dateien, 1 Fehler“) berichtet.

9.2 get -r (Ordner herunterladen)

  1. Remote-Verzeichnisbaum ab <remote> rekursiv traversieren — mit der bereits vorhandenen list-Action (ein HTTP-Request pro Unterverzeichnis, keine Server-Änderung nötig).
  2. Für jedes Remote-Unterverzeichnis lokal localfs_mkdir() aufrufen.
  3. Für jede Remote-Datei bestehende Download-Logik aus cmd_get wiederverwenden.
  4. Gleiche Fortschritts-/Fehlersammel-Logik wie bei put -r.

9.3 del -r (Ordner inkl. Inhalt löschen)

Destruktiv — Sicherheitsabfrage zwingend

Vor der Ausführung fragt die Shell Delete '/pfad' and ALL contents? [y/N]. Nur bei y/yes wird gelöscht. Das Force-Flag (-f / --force / FORCE, Abschnitt 8.1) unterdrückt die Abfrage für Skript-/Batch-Nutzung — bestätigt per Nutzer-Feedback, Standardverhalten bleibt „nachfragen“.

Entschieden: Variante B ist das Zielbild (Server-Deploy ist kein Hindernis), Variante A bleibt als automatischer Fallback bestehen:

VarianteAblaufVor-/Nachteile
A — rein client-seitig
(Fallback)		Baum rekursiv per list einlesen, dann bottom-up löschen: erst alle Dateien, dann Verzeichnisse von den tiefsten zu den flachsten (jede Löschung ein bestehender delete-Call, der auf leere Dirs/Files schon funktioniert)Kein Server-Deploy nötig; aber 1 Request pro Datei/Verzeichnis, nicht atomar (bei Abbruch bleibt Teilbaum übrig)
B — Server-seitig GEWÄHLT
DELETE …&recursive=1		Server löscht Baum in einem Request inkl. DB-Aufräumen (DELETE FROM files WHERE path LIKE 'prefix/%')Ein Request, atomar aus Nutzersicht, weniger Netzwerk-Overhead — erfordert Server-Deploy (siehe Abschnitt 10.1)

Client versucht immer zuerst recursive=1; bekommt er dafür 400 „Unknown parameter“ o. ä. von einem (noch) nicht aktualisierten Server, fällt er automatisch auf Variante A zurück. Damit funktioniert die Shell auch gegen einen älteren Server, ohne dass man beide Seiten gleichzeitig deployen muss.

10. Server-seitige Änderungen

Zwei kleine, klar umgrenzte Erweiterungen in server/includes/FileStore.php und server/api.php:

10.1 Rekursives Löschen

EndpointDELETE api.php?action=delete&path=/ordner&recursive=1
VerhaltenBisher: rmdir() schlägt bei nicht-leerem Verzeichnis mit 409 fehl. Neu: bei recursive=1 und is_dir($target) wird der Baum rekursiv gelöscht (Dateien unlink, Verzeichnisse bottom-up rmdir) und alle zugehörigen Zeilen per DELETE FROM files WHERE user_id=? AND (path=? OR path LIKE 'prefix/%') entfernt (gleiches Präfix-Muster wie bereits bei renameImpl() für Kind-Pfade verwendet).
AbwärtskompatibelOhne recursive-Parameter unverändertes Verhalten (409 bei nicht-leer) — bestehende del-Nutzung im Nicht-Shell-Client bleibt unberührt.

10.2 Status-/Versions-Auskunft

EndpointGET api.php?action=status NEU
Antwort{"status":"ok","version":"0.1","time":"2026-…Z"} — version kommt aus einer neuen Konstante, die mit AMICLOUD_VERSION aus web.php synchron gehalten wird (z. B. gemeinsame Definition in config.php oder eigener includes/Version.php).
ZweckEinzige fehlende Zutat für den Start-Banner der Shell (Abschnitt 6) — verlangt Basic Auth wie alle anderen Actions, dient zugleich als Verbindungs-/Health-Check.

Entschieden: bewusst minimal — kein Speicherplatz-/Quota-Feld. Es gibt im Schema aktuell kein Quota-Konzept (files-Tabelle kennt keine Limits, nur Ist-Größen), das wäre eine eigenständige Baustelle unabhängig von der Shell. Version + Health-Check reichen für den Banner völlig aus.

10.3 Rekursive Verzeichnisgröße für info NEU

Bisher liefert FileStore::info() für Verzeichnisse immer size: 0. Neue Anforderung: info/stat auf ein Verzeichnis soll die Gesamtgröße aller enthaltenen Dateien inklusive aller Unterverzeichnisse liefern.

UmsetzungIn FileStore::info(): wenn $isDir, statt filesize() eine rekursive Summe bilden — z. B. mit PHPs RecursiveDirectoryIterator/RecursiveIteratorIterator direkt über das Dateisystem (robust, unabhängig davon ob jede Unterverzeichnis-Zeile in der DB existiert). Alternative wäre eine DB-Summe über size_bytes mit Pfad-Präfix-Filter (schneller, aber nur so genau wie die DB-Pflege) — Dateisystem-Variante wird empfohlen, weil sie immer korrekt ist und zum bisherigen Stil des Codes passt (einfach, ohne Zusatzabhängigkeit von DB-Konsistenz).
ScopeBetrifft ausschließlich die info-Action für ein explizit angefragtes Verzeichnis. list zeigt Verzeichniseinträge weiterhin mit size: 0 — pro Zeile in einer Auflistung rekursiv zu summieren würde die Kosten mit der Anzahl der Unterordner multiplizieren und ist nicht Teil der Anforderung.
Performance-HinweisFür sehr große Bäume läuft die Berechnung synchron im selben Request — bei einer Cloud für persönliche Nutzung (kein Massenspeicher-Dienst) unkritisch, aber erwähnenswert als Grenze dieses einfachen Ansatzes.

Client-seitig ist keine Änderung nötig: cmd_info() gibt bereits unverändert das size-Feld aus der Server-Antwort aus (client/cmd.c, jlong(root, "size")) — profitiert also automatisch, sowohl im Einzelkommando amicloud info als auch im Shell-Befehl info/stat.

Damit ist auch die Anforderung „ganzen Ordner herunterladen, analog zu Dateien“ vollständig abgedeckt: get -r (Abschnitt 9.2) lädt einen Remote-Ordner exakt so herunter wie get eine einzelne Datei — gleiche Argumentreihenfolge, gleiches Zielverzeichnis-Verhalten, nur eben rekursiv.

Beide Server-Ergänzungen (status, info-Rekursivgröße) plus recursive=1 bei delete werden in docs/API.md nachgetragen (neue Action-Abschnitte + Fehlercode-Tabelle bleibt gültig) und in scripts/test_api.sh um passende Checks erweitert.

12. Fehlerbehandlung & Sicherheit

  • Kein Kommandofehler beendet die Shell — nur quit/exit/EOF.
  • del -r verlangt Bestätigung (s. 9.3); Batch-Betrieb via Force-Flag möglich.
  • Pfad-Traversal-Schutz bleibt serverseitig bestehen (sanitizePath); cd normalisiert alle Kurzsymbole (Abschnitt 8.2) vor dem Versand, andere Befehle (get/put/mkdir …) verhalten sich wie bisher — ein direkt übergebenes .. außerhalb von cd bleibt (wie heute schon) ein Server-Fehler 400, das ändert sich nicht.
  • Zugangsdaten werden wie bisher einmal beim Start geladen; es gibt in dieser ersten Version keinen connect/open-Befehl zum Umschalten auf einen anderen Server innerhalb der Session (bewusst außerhalb des Scopes, siehe Abschnitt 14).

14. Entscheidungsstand

Alle Design-Fragen entschieden — Plan ist umsetzungsreif

  • Flag-Syntax: kein -r vs. Wortbefehl-Entweder-oder — alle drei Schreibweisen (kurz/lang/Amiga-Keyword) sind auf jeder Plattform gleichzeitig gültig, s. Abschnitt 8.1.
  • cd/lcd-Kurzsymbole: plattform-native Interpretation für den einen echten Konflikt (/), universelle Aliase für alles Kollisionsfreie (.., :, \), s. Abschnitt 8.2.
  • Bestätigungsverhalten bei del -r: Sicherheitsabfrage ist Standard, Force-Flag zum Überspringen.
  • Rekursives Löschen: Server-seitig (Variante B) ist das Zielbild, client-seitige Variante A bleibt automatischer Fallback für nicht aktualisierte Server, s. Abschnitt 9.3.
  • Prompt-Format: kein amicloud:-Präfix, reiner Remote-Pfad mit plattform-nativem Root-Symbol (:///\), s. Abschnitt 6.1.

17. Fortschrittsanzeige: Datei-Zähler + Byte-Prozent bei get/put v4

Bei allen Mehrdatei-Operationen (Wildcard-get/put, get -r/put -r, später auch sync) bekommt jede übertragene Datei einen Präfix aus Datei-Zähler x/y und Prozentwert. Der Prozentwert bezieht sich auf die übertragenen Bytes, nicht auf die Dateianzahl — bei einem Ordner mit einer großen und vielen kleinen Dateien zeigt er also den echten Übertragungsfortschritt: 

( 3/12  47%) Downloaded fotos/img_003.jpg
( 4/12  48%) Downloaded fotos/img_004.jpg
...
(12/12 100%) Downloaded fotos/readme.txt
12 Datei(en) ok, 0 Fehler

17.1 Zwei Durchläufe: erst zählen & summieren, dann übertragen

Damit y (Gesamtzahl) und total_bytes (Gesamtvolumen) vor der ersten Übertragung feststehen, wird pro Operation ein Zähl-Durchlauf vorgeschaltet — die Dateigrößen fallen dort gratis mit ab:

OperationWoher kommen y und total_bytes?Kosten
Wildcard (get *.txt / put #?.c)Die Treffer stehen nach dem ohnehin nötigen list-/localfs_opendir-Durchlauf fest — dazu wird die bestehende Schleife in do_get_pattern()/do_put_pattern() zweigeteilt: erst Treffer sammeln (Array statt Sofort-Transfer, AcEntry.size/LocalDirEntry.size aufsummieren), dann übertragen.keine zusätzlichen Requests
get -rVor-Traversierung des Remote-Baums per cmd_list_raw() — Anzahl und Byte-Summe aus den size-Feldern; danach die bestehende shell_get_dir()-Rekursion mit mitlaufendem Zähler.1 zusätzlicher list-Request pro Unterverzeichnis — derselbe Baum wird gleich darauf sowieso gelistet; alternativ kann der Zähl-Durchlauf die Einträge gleich cachen (Entscheidung bei Implementierung, Cache spart die Hälfte der list-Requests)
put -rVor-Traversierung des lokalen Baums per localfs (Anzahl + Byte-Summe) — rein lokal, praktisch kostenlos.keine Requests

17.2 Prozent-Semantik & Umsetzung ohne Änderung an cmd.c

cmd_get()/cmd_put() geben bereits Downloaded …/Uploaded … aus. Die Shell druckt den Präfix ( x/y  p%)  (ohne Zeilenumbruch, fflush) unmittelbar davor — die bestehende Ausgabezeile von cmd.c vervollständigt sie. Der Prozentwert ist p = (bytes_done + size_dieser_datei) / total_bytes, also der Stand nach Abschluss der gerade laufenden Datei — so endet die letzte Zeile immer bei 100% und der Wert neben einer Zeile beschreibt genau das, was diese Zeile geleistet hat. Der Fortschritt aktualisiert sich damit an Dateigrenzen (byte-genau kumuliert), nicht innerhalb einer Datei — s. Kasten unten. Fehlerfälle schreiben nach stderr und stören den Zähler nicht: gescheiterte Dateien zählen in x weiter und ihre Bytes werden trotzdem als „verbraucht“ verbucht, sonst käme der Lauf nie bei 100 % an. Dafür wandern die bisherigen losen int *ok, *err-Parameter in eine Struktur Progress { int done, total, ok, err; long bytes_done, bytes_total; }, die durch shell_get_dir()/shell_put_dir()/die Pattern-Schleifen gereicht wird.

  • Einzeldatei-get/put: unverändert, kein (1/1 100%)-Präfix — bringt keine Information.
  • Zeilenbreite: Präfix kostet maximal 13 Zeichen ((12/12 100%) ) — bleibt mit den bestehenden gekürzten Ausgaben unter den ~70 Zeichen für schmale Amiga-Konsolen.
  • 0-Byte-Sonderfall: total_bytes == 0 (nur leere Dateien) → Prozentanzeige entfällt, nur x/y.

Abgrenzung: Prozent innerhalb einer einzelnen Datei

Ein live mitlaufender Balken während einer einzelnen großen Übertragung bräuchte einen Fortschritts-Callback in der HTTP-Schicht (http_download/http_request in beiden Implementierungen, auf dem Amiga zusätzlich Umbau der blockierenden Sende-/Empfangsschleife). Das bleibt eine mögliche spätere Erweiterung — die hier geplante byte-kumulierte Anzeige an Dateigrenzen liefert bereits echte Byte-Prozent über den Gesamtlauf, ohne die HTTP-Schicht anzufassen.

18. MD5-Prüfsummen: Übertragungscheck & Sync-Grundlage v4

Jede Datei bekommt serverseitig eine gespeicherte Prüfsumme. Sie dient (a) als Übertragungscheck bei get/put und (b) als Vergleichsbasis für sync (Abschnitt 20).

18.1 Algorithmuswahl: MD5, eingebettet im Code — entschieden

KandidatBewertung
CRC-8/16/32Wie in der Anforderung festgestellt: zu kollisionsanfällig für Sync-Entscheidungen (32 Bit ≙ Zufallskollision schon bei ~65k Dateien realistisch) — raus.
SHA-256 (AmiSSL)Kryptographisch überdimensioniert und auf 68030/68040 spürbar langsam; außerdem wäre der PC-Client dann auf eine Crypto-Bibliothek angewiesen, die er heute nicht linkt (libcurl macht TLS intern) — raus.
MD5 via AmiSSLFunktioniert auf dem Amiga (AmiSSL ist dort für HTTPS eh geladen), aber: auf dem PC gibt es kein AmiSSL, d. h. zwei Codepfade; zudem bindet es die Prüfsumme an die TLS-Initialisierung — raus.
MD5 als eigene portable C-Datei GEWÄHLTReferenzimplementierung nach RFC 1321 (Public Domain, ~250 Zeilen C89) als client/md5.c/md5.h — identischer Code auf allen vier Plattformen, keine neue Abhängigkeit, auf 68k deutlich schneller als SHA. 128 Bit sind für Integritäts-/Sync-Zwecke (nicht-adversarial) mehr als eindeutig genug; die bekannten MD5-Kollisionsangriffe sind hier irrelevant, weil niemand gezielt Kollisionen konstruiert.

Serverseitig rechnet PHP nativ: md5($data) / md5_file($path) — kein Zusatzmodul nötig. Wire-Format: 32 Hex-Zeichen, kleingeschrieben, JSON-Feld md5.

18.2 Server: Speicherung & API

BausteinÄnderung
server/sql/migrate_002.sql NEUALTER TABLE files ADD COLUMN checksum CHAR(32) NULL — NULL = „noch nicht berechnet“ (Bestandsdateien, Verzeichnisse).
upload (API) + uploadRaw (Web)Berechnet md5 des Bodys und schreibt es mit in die files-Zeile; Antwort enthält neu "md5":"…". Übertragungscheck: optionaler Parameter &md5=<hex> — stimmt er nicht mit dem empfangenen Body überein, HTTP 422 bevor die Datei geschrieben wird (Client wiederholt oder meldet Fehler). 18.3 Client: Verifikation bei get/put

  • put: cmd_put() hat die Datei bereits komplett im RAM → md5(data) ist ein Einzeiler, wird als &md5= an die Upload-URL gehängt. Ein alter Server ignoriert den unbekannten Parameter einfach → funktioniert gegen jeden Deploy-Stand.
  • get: Die MD5 wird während des Schreibens mitgerechnet (Streaming-Update im Download-Pfad) und am Ende gegen X-AmiCloud-MD5 verglichen. Dafür braucht die HTTP-Schicht zwei kleine Erweiterungen: http_download() bekommt einen optionalen Md5Ctx* (beide Implementierungen füttern ihn im Write-Pfad), und die Antwortstruktur transportiert genau diesen einen Header (neues Feld char md5_header[33] in HttpResponse — bewusst kein generischer Header-Store). Fehlt der Header (alter Server, Teil-Download), wird die Prüfung übersprungen, kein Fehler.
  • Mismatch bei get: Fehlermeldung, Rückgabewert „Fehler“ (zählt in x/y-Läufen als Fehler), die unvollständige lokale Datei wird gelöscht — keine halb-kaputten Dateien auf Platte.
  • Verify ist Standard, nicht optional — kein neues Flag; die Kosten (ein MD5-Durchlauf über Daten, die sowieso durch die CPU laufen) sind auch auf 68k vertretbar.

18.4 Anzeige-Flag bei ls/lls: -m/--md5/MD5 v4.1

Die Listen-Befehle bekommen einen vierten Anzeige-Modus neben -n/-s/-d: neuer ListMode-Wert LIST_MD5, Spalten Name + MD5 (32 Hex-Zeichen — Name wird dafür wie in LIST_FULL auf 28 Zeichen gekürzt, Zeile bleibt unter ~64 Zeichen). Erkennung im bestehenden parse_list_mode()-Muster, gleiche Drei-Schreibweisen-Regel wie alle Flags.

BefehlWoher kommt die MD5?Kosten

19. Zeitstempel: UTC intern, lokale Anzeige — Amiga-Zeitzonen-Config v4

sync braucht vergleichbare Zeitstempel über Rechnergrenzen hinweg. Heute liefert der Server bewusst lokale Zeit-Strings (AMICLOUD_TIMEZONE, „YYYY-MM-DD HH:MM:SS“) — das bleibt für die Anzeige (ls/info/Web) unverändert. Für den Vergleich kommt ein maschinenlesbares Feld dazu:

BausteinÄnderung
list / info / upload-AntwortNeues Feld "mtime": <unix-epoch-sekunden, UTC> pro Eintrag — serverseitig trivial (filemtime() liefert bereits Epoch). Das bestehende "modified"-String-Feld bleibt unverändert erhalten (Anzeige, Handler, Abwärtskompatibilität).
setdateAkzeptiert alternativ &mtime=<epoch> statt &modified=<string> — damit kann der Client nach einem Sync-Upload die Remote-Mtime exakt (und zeitzonenfrei) auf die Quelldatei setzen. Der bestehende String-Parameter bleibt für den Handler erhalten.

19.1 Client-Seite: Epoch pro Plattform

PlattformLokale Datei-Mtime als UTC-Epoch

  • Neue localfs-Funktionen für Sync: localfs_stat(path, &size, &mtime_epoch) und localfs_utime(path, mtime_epoch) (PC: stat/utime; Amiga: Examine/SetFileDate + obige Umrechnung). Das bestehende Anzeige-Feld LocalDirEntry.modified bleibt unangetastet; LocalDirEntry bekommt zusätzlich long mtime.
  • Toleranz: Zeitstempel gelten als gleich bei |Δ| ≤ 2 s (FAT-Auflösung, Amiga-Ticks, Rundung bei der Übertragung).

20. sync — bidirektionaler Ordnerabgleich v4

20.1 Aufruf

FormBedeutung
synclocal_cwd ↔ remote_cwd (die aktuellen Verzeichnisse der Session)
sync <lokal>angegebener lokaler Ordner ↔ remote_cwd
sync <lokal> <remote>beide explizit — Argumentreihenfolge wie bei put (lokal zuerst); lokal darf jeder native Pfad inkl. anderer Laufwerke sein (Abschnitt 21), remote wird wie überall relativ zu remote_cwd bzw. mit führendem / ab Wurzel aufgelöst

sync ist immer rekursiv (ein Ordnerabgleich ohne Unterordner wäre keiner); ein -n/--dry-run/NOOP-Flag zeigt nur an, was passieren würde, ohne zu übertragen — dringend empfohlen für den ersten Lauf.

20.2 Ablauf

  1. Indizes bauen: Remote-Baum rekursiv per cmd_list_raw() (liefert nach Abschnitt 18/19 pro Datei size, md5, mtime); lokaler Baum per localfs-Traversal (size, mtime; MD5 lokal erst bei Bedarf rechnen, s. Matrix — spart auf dem Amiga Plattenlesezeit).
  2. Aktionsliste ableiten (Matrix 20.3), Gesamtzahl = y für die Fortschrittsanzeige.
  3. Ausführen mit ( x/y)-Zähler (Abschnitt 17); fehlende Verzeichnisse werden auf der Zielseite angelegt (mkdir-Action bzw. localfs_mkdir).
  4. Mtime angleichen: nach jedem Kopieren erhält die Zielseite die Mtime der Quelle — lokal per localfs_utime(), remote per setdate&mtime= (Abschnitt 19). Ohne diesen Schritt würde jede kopierte Datei beim nächsten Lauf erneut als „neuer“ gelten.
  5. Zusammenfassung: 3 hochgeladen, 1 heruntergeladen, 40 unveraendert, 1 Konflikt (uebersprungen).

20.3 Entscheidungsmatrix

FallAktion

Nur remote vorhandenDownload (get)

Bewusste, dokumentierte Grenze dieser Version; Löschen weiterhin explizit per del. (Eine spätere Version könnte eine lokale Sync-Statusdatei einführen.)

Warum MD5 vor Mtime entscheidet

Mtime allein ist über Amiga↔PC↔Server hinweg das fragilste Kriterium (Zeitzonen-Config, DST-Wechsel, ungestellte Amiga-Uhr). Die Prüfsumme beantwortet die wichtigste Frage — „ist die Datei verschieden?“ — absolut zuverlässig; die Mtime entscheidet nur noch die Richtung, wenn feststeht, dass kopiert werden muss. Eine falsch gestellte Uhr kann so schlimmstenfalls die falsche Version gewinnen lassen, aber nie unnötige Übertragungen oder Endlos-Sync-Schleifen erzeugen.

21. Freie lokale Pfade bei get/put (andere Laufwerke) v4

Anforderung: der lokale Pfad darf jeder native Pfad sein — auch andere Laufwerke (DH1:Downloads, Work:tmp/x, C:\Daten, /Volumes/USB/x). Remote bleibt wie bisher: relativ zu remote_cwd, führendes / = ab Wurzel (bestätigt das Ist-Verhalten von full_path()).

21.1 Ist-Zustand & Lücken

  • Einzeldatei-get/put: reichen den lokalen Pfad direkt an fopen() durch — native Pfade inkl. Laufwerke funktionieren hier heute schon. Keine Änderung.
  • Wildcard-/Rekursiv-Zweige (und künftig sync): hier liegt die Lücke. join_local() und die snprintf("%s/%s")-Stellen in shell_get_dir()/do_get_pattern() hängen stur / an — aus DH1: würde DH1:/name (auf AmigaDOS „Parent der Root“, ungültig), aus C:\Daten würde C:\Daten/name (funktioniert zwar meist, ist aber inkonsistent).

BausteinVerhalten

  • Neue Spalte MD5 zwischen „Größe“ und „Geändert“ — die Daten liefert listRaw() automatisch mit, sobald scanEntries() das md5-Feld führt (18.2, gemeinsamer Codepfad von API-list und Web-Listing, inkl. Lazy Backfill beim ersten Aufruf).
  • Darstellung: 32 Hex-Zeichen sprengen die Tabelle — angezeigt werden die ersten 10 Zeichen in <code>-Schrift, der volle Wert steht im title-Tooltip und die Zelle ist per Klick markierbar (volle Summe als Textinhalt eines <span> mit CSS-Kürzung text-overflow: ellipsis — so kopiert Doppelklick/Strg-C immer den vollen Wert, ohne JavaScript). Verzeichnisse: — wie bei der Größe.
  • Responsive-Verhalten: auf schmalen Viewports wird die MD5-Spalte per bestehendem CSS-Muster ausgeblendet (Prüfsummen-Vergleich ist ein Desktop-Anwendungsfall).
