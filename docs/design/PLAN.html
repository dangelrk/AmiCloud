1 — Ziele & Umfang

In Scope (Minimum)

  • Dateien hochladen & herunterladen
  • Unterordner-Unterstützung
  • Datei löschen
  • Dateiinformationen abfragen (Größe, Datum)
  • Verzeichnisinhalt auflisten
  • Einfache Benutzerverwaltung (User + Passwort)
  • Konsolen-Client PC (Mac/Linux/Windows)
  • Konsolen-Client Amiga (VBCC, nativ)
  • HTTPS von Anfang an — Let's Encrypt + AmiSSL

Geplante Erweiterung

  • AmigaOS Filesystem-Handler — CLOUD: als normales Amiga-Laufwerk einbinden (AmiCloud-REST; kein WebDAV im Handler, siehe unten)
  • Webinterface — Login + Dateibrowser im Browser (kein Framework, reines PHP/HTML)
  • Token-Authentifizierung
  • Mehrbenutzer-ACL
  • Speicherquoten pro User
  • Amiga-GUI-Client (MUI)
  • Umgesetzt als eigenständiges Projekt statt Brücke: AmiCloudSync — ein separates Commodity, das per WebDAV mit einem Standard-OwnCloud/Nextcloud-Server synchronisiert (kein gemeinsamer Speicher mit AmiCloud, kein Handler-Code, keine expat.library — siehe docs/user/AmiCloudSync-Handbuch.html)

Out of Scope (vorerst)

  • Versionierung von Dateien
  • Sharing-Links
  • Quota-Management

Kein Apache-Eingriff: PHP ist auf dem Server bereits aktiv (OwnCloud läuft). AmiCloud wird als einfaches Unterverzeichnis unter dem bestehenden DocumentRoot abgelegt. Kein neuer vHost, kein mod_rewrite, keine Apache-Konfigurationsänderung.
TLS: Let's Encrypt-Zertifikat ist bereits vorhanden und deckt das Unterverzeichnis automatisch ab. Alle Clients sprechen ausschließlich HTTPS.
Amiga-Compiler: VBCC (nativ auf dem Amiga), da kein Cross-Compiling gewünscht. VBCC ist ein moderner, freier C-Compiler mit guter AmigaOS-Unterstützung.

3 — HTTPS-API-Protokoll

Alle Anfragen laufen ausschließlich über HTTPS. Authentifizierung via HTTP Basic Auth (Authorization: Basic base64(user:pass)) — durch TLS vollständig gesichert. Für VBCC/Amiga ideal: nur Base64 nötig, kein Token-State.

HTTP/1.0 mit Connection: close reicht für alle Clients — kein Chunked Transfer, kein Keep-Alive. Der PHP-Server antwortet auf HTTP/1.0 und HTTP/1.1 gleichermaßen.
Zertifikat-Validierung auf dem Amiga: AmiSSL 5.27 (OpenSSL 3.x-Basis) kennt ISRG Root X1 (Let's Encrypt). Debug-Flag -k deaktiviert die Prüfung (nur für Entwicklung).

Endpunkte

MethodePfadFunktionBodyResponse
GET /amicloud/api.php?action=list&path=/sub Verzeichnis auflisten— JSON-Array
GET /amicloud/api.php?action=download&path=/sub/f Datei herunterladen— Rohe Dateidaten
POST /amicloud/api.php?action=upload&path=/sub/f Datei hochladen Rohe Bytes im Body JSON Status
DELETE /amicloud/api.php?action=delete&path=/sub/f Datei löschen— JSON Status
GET /amicloud/api.php?action=info&path=/sub/f Dateiinfos— JSON (name, size, created, modified)
POST /amicloud/api.php?action=mkdir&path=/new Ordner erstellen— JSON Status
GET /amicloud/api.php?action=download&path=/f&offset=N&length=M Teildownload (für Filesystem-Handler / Seek-Unterstützung)— Rohe Bytes (M Bytes ab Offset N)
Der offset/length-Parameter beim Download wird intern via PHP fseek() + fread() implementiert und ist wichtig für den Filesystem-Handler (der AmigaOS ACTION_SEEK-Pakete empfangen kann). Für den CLI-Client wird er nicht benötigt.

Authentifizierung

  • HTTP Basic Auth per Request — durch HTTPS sicher.
  • Passwörter in der DB als bcrypt-Hash.
  • Stateless — kein Session-Cookie, kein Token (Amiga/Filesystem-Handler-freundlich).
  • Erweiterungspunkt: Bearer-Token ohne Basic Auth zu entfernen nachrüstbar.

4 — Serverkomponente

PHP 7.4 Alma Linux 9.8 Let's Encrypt
Der Server läuft auf PHP 7.4 — ein Upgrade ist nicht möglich, solange OwnCloud diese Version voraussetzt. AmiCloud ist daher bewusst auf PHP-7.4-kompatible Syntax beschränkt (kein match, kein ??=, keine Union Types etc.).

Server-Verzeichnisstruktur (Ist-Zustand)

Der Server hat folgende bestehende Verzeichnisstruktur:

/var/www/html/          ← Eigene Webseite (eigener Apache-vHost)
/var/www/owncloud/      ← OwnCloud (eigener Apache-vHost, eigenes Let's-Encrypt-Zertifikat)
/var/www/cgi-bin/       ← CGI-Skripte
AmiCloud bekommt — analog zu OwnCloud — ein eigenes Verzeichnis auf der gleichen Ebene (/var/www/amicloud/) mit einem eigenen Apache-VirtualHost und einem eigenen Let's-Encrypt-Zertifikat für die Subdomain amicloud.example.com.

Dateistruktur auf dem Server (nach Deployment)

/var/www/html/                   ← Eigene Webseite (unverändert)
/var/www/owncloud/               ← OwnCloud (unverändert, eigener vHost)
/var/www/amicloud/               ← NEU: AmiCloud (eigener vHost, analog OwnCloud)

    config.php.example           ← Template

        Auth.php

Deployment

Schritt 1 — DNS

Beim DNS-Provider einen A-Record anlegen, der auf dieselbe Server-IP zeigt: 

amicloud.example.com.   IN   A   <Server-IP>

Schritt 2 — Apache VirtualHost

Neue Datei /etc/httpd/conf.d/amicloud.conf anlegen (berührt keine bestehende Config): 

<VirtualHost *:80>
    ServerName   amicloud.example.com
    DocumentRoot /var/www/amicloud
    DirectoryIndex disabled

    <Directory /var/www/amicloud>
        Options None
        AllowOverride All
        Require all granted
    </Directory>
</VirtualHost>

Schritt 3 — Let's Encrypt Zertifikat

sudo certbot --apache -d amicloud.example.com

Certbot ergänzt die Config automatisch um einen HTTPS-Block und richtet den Redirect HTTP→HTTPS ein.

Schritt 4 — PHP-Dateien deployen

# Verzeichnisse anlegen:
sudo mkdir -p /var/www/amicloud
sudo mkdir -p /var/amicloud-storage

# Dateien kopieren (von deinem Rechner aus via scp):
scp -r server/* user@server:/var/www/amicloud/

# Config anlegen und anpassen:
sudo cp /var/www/amicloud/config.php.example /var/www/amicloud/config.php
sudo nano /var/www/amicloud/config.php        # DB-Daten + Storage-Pfad eintragen

# Berechtigungen (Apache-User auf AlmaLinux heißt "apache"):
sudo chown -R apache:apache /var/www/amicloud/
sudo chown -R apache:apache /var/amicloud-storage/
sudo chmod 750 /var/amicloud-storage/

Schritt 5 — Apache neu laden

sudo systemctl reload httpd

Danach ist die API erreichbar unter:
https://amicloud.example.com/api.php
Das ist der Wert für server= in der Client-Config (ohne /api.php).

Der Storage-Pfad (/var/amicloud-storage/) liegt außerhalb aller Web-Roots und ist damit nicht direkt per HTTP erreichbar — auch ohne .htaccess-Schutz.

Schutz von includes/ ohne .htaccess

Falls .htaccess nicht aktiviert ist (kein AllowOverride), schützen wir includes/ programmatisch: Jede Include-Datei prüft, ob sie direkt aufgerufen wurde: 

<?php
// Erste Zeile in jeder includes/*.php:
if (!defined('AMICLOUD')) { http_response_code(403); exit; }

In api.php steht vor allen Includes: define('AMICLOUD', 1);

Kern-Logik api.php

<?php
define('AMICLOUD', 1);
require 'config.php';
require 'includes/DB.php';
require 'includes/Auth.php';
require 'includes/FileStore.php';
require 'includes/Response.php';

Auth::requireBasicAuth();           // 401 wenn fehlgeschlagen
$action = $_GET['action'] ?? '';
$path   = sanitizePath($_GET['path'] ?? '/');

switch ($action) {
    case 'list':     FileStore::list($path); break;
    case 'download': FileStore::download($path,
                         (int)($_GET['offset'] ?? 0),
                         (int)($_GET['length'] ?? -1)); break;
    case 'upload':   FileStore::upload($path, file_get_contents('php://input')); break;
    case 'delete':   FileStore::delete($path); break;
    case 'info':     FileStore::info($path); break;
    case 'mkdir':    FileStore::mkdir($path); break;
    default:         Response::error(400, 'Unknown action');
};

Sicherheitsregeln

  • Path Traversal: sanitizePath() blockt ../ und Pfade außerhalb des User-Verzeichnisses.
  • Storage außerhalb des Web-Roots — kein direkter HTTP-Zugriff möglich.
  • Passwörter nur als bcrypt-Hash.
  • HTTPS erzwungen (PHP-seitig prüfen: $_SERVER['HTTPS'] !== 'on' → Redirect oder Fehler).
  • config.php steht in .gitignore.

5 — Datenbank (MariaDB)

MariaDB

Datenbank und Benutzer anlegen

AmiCloud bekommt eine eigene Datenbank und einen eigenen MariaDB-Benutzer mit minimalen Rechten — kein Root-Zugriff aus PHP. 

# Als root auf dem Server:
mysql -u root -p

-- Datenbank anlegen:
CREATE DATABASE amicloud
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;

-- Dedizierter Benutzer (nur localhost, nur diese DB):
CREATE USER 'amicloud'@'localhost' IDENTIFIED BY 'SICHERES_PASSWORT_HIER';
GRANT SELECT, INSERT, UPDATE, DELETE
    ON amicloud.*
    TO 'amicloud'@'localhost';
FLUSH PRIVILEGES;

-- Schema einspielen:
USE amicloud;
SOURCE /var/www/amicloud/sql/schema.sql;

-- Prüfen:
SHOW GRANTS FOR 'amicloud'@'localhost';
EXIT;
Nur die vier nötigen DML-Rechte (SELECT, INSERT, UPDATE, DELETE) werden vergeben — kein DROP, kein CREATE, kein ALTER aus der PHP-Anwendung heraus. Das Schema wird einmalig manuell eingespielt (s. oben) oder beim ersten Deployment als separater Schritt ausgeführt.

Danach in config.php eintragen: 

<?php
define('DB_HOST', 'localhost');
define('DB_NAME', 'amicloud');
define('DB_USER', 'amicloud');           // der neue Benutzer
define('DB_PASS', 'SICHERES_PASSWORT_HIER');
define('STORAGE_PATH', '/var/amicloud-storage');
define('MAX_UPLOAD',   100 * 1024 * 1024);

Schema

CREATE TABLE users (
    id          INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    username    VARCHAR(64)  NOT NULL UNIQUE,
    pass_hash   VARCHAR(255) NOT NULL,           -- bcrypt
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    active      TINYINT(1) DEFAULT 1
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE files (
    id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id     INT UNSIGNED NOT NULL,
    path        VARCHAR(1024) NOT NULL,           -- relativ zu storage/{user}/
    size_bytes  BIGINT UNSIGNED DEFAULT 0,
    mime_type   VARCHAR(128),
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    modified_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    is_dir      TINYINT(1) DEFAULT 0,
    UNIQUE KEY uq_user_path (user_id, path(768)),
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
Die DB speichert nur Metadaten — die Bytes liegen im Filesystem. Erweiterungspunkte: quota_bytes, checksum (SHA-256), share_links-Tabelle.

Benutzer anlegen — bcrypt-Hash erzeugen

Das Feld pass_hash enthält keinen Klartext, sondern einen bcrypt-Hash (PHP PASSWORD_BCRYPT). Den Hash erzeugst du einmalig auf der Konsole: 

# PHP muss installiert sein (php -v zum Prüfen; macOS: brew install php)
php -r "echo password_hash('DeinPasswort', PASSWORD_BCRYPT) . PHP_EOL;"
# Ausgabe z.B.: $2y$10$abc123...

Den Hash dann direkt in die DB eintragen:

-- Neuen Benutzer anlegen:
INSERT INTO users (username, pass_hash, active)
VALUES ('bob', '$2y$10$abc123...', 1);

-- Passwort eines bestehenden Benutzers ändern:
UPDATE users SET pass_hash = '$2y$10$abc123...' WHERE username = 'bob';
Niemals den Klartext direkt in pass_hash eintragen — password_verify() in Auth.php erwartet ausschließlich den bcrypt-Hash. Der Hash ändert sich bei jedem Aufruf von password_hash() (Salt ist eingebettet), das ist korrekt und gewollt.

6 — Client-Programm PC

C Linux macOS Windows libcurl TLS
Sprache: C (nicht C++), damit ~70 % des Codes mit dem Amiga-Client geteilt werden. HTTPS via libcurl — TLS ist transparent, kein extra Aufwand.

Kommandozeileninterface

7 — Client-Programm Amiga

C AmigaOS 3.x AmiSSL 5.27

Compiler: VBCC (nativ auf dem Amiga)

VBCC (Volker Barthelmann C Compiler) ist ein moderner, freier ISO-C-Compiler der direkt unter AmigaOS läuft — kein Cross-Compiling nötig. Für den Amiga-Client wird nativ auf dem Amiga kompiliert.

  • VBCC für m68k-AmigaOS installiert in vbcc/ (oder systemweit)
  • Targets: m68k-amigaos (Standard), optional m68000 für maximale Kompatibilität
  • AmiSSL SDK-Header im VBCC-Includepfad eintragen
  • Linker: vlink (kommt mit VBCC)
  • Alternativ SAS/C 6.x — Makefile.amiga wird für beide Compiler-Varianten kommentiert

Minimales VBCC-Makefile-Snippet

# Makefile.amiga (VBCC) — tatsächliche Pfade
CC           = vc
ROADSHOW_INC = Dev:SDK/Roadshow/netinclude
AMISSL_INC   = Dev:SDK/AmiSSL/Developer/include

CFLAGS = +aos68k -O2 -DAMIGA -DPLATFORM_AMIGA \
         -I$(ROADSHOW_INC) -I$(AMISSL_INC) \
         -cpu=68000
LDFLAGS = +aos68k
# cJSON wird direkt mitkompiliert — keine externe Library noetig.
# amisslmaster, amissl, bsdsocket: AmigaOS-Runtime-Libraries (.library),
# werden per OpenLibrary() geoeffnet — keine statischen Link-Libraries.
# -lvc und startup.o werden von VBCC via +aos68k automatisch hinzugefuegt.

OBJS = main.o cmd.o http_amiga.o base64.o config.o cJSON.o

amicloud: $(OBJS)
    $(CC) $(LDFLAGS) -o amicloud $(OBJS)

.c.o:
    $(CC) $(CFLAGS) -c $<

Voraussetzungen Amiga

  • AmigaOS 3.1+
  • GNUMake — VBCC enthält kein make; GNUMake von Aminet: util/gnu/GNUmake.lha
  • Roadshow SDK — TCP/IP-Headers (Dev:SDK/Roadshow/netinclude); liefert proto/socket.h, netdb.h, sys/socket.h usw.; NDK-Basis-Headers findet VBCC automatisch
  • AmiSSL 5.27 SDK — Headers unter Dev:SDK/AmiSSL/Developer/include; TLS-Layer auf Basis OpenSSL 3.x, inkl. ISRG Root X1 (Let's Encrypt)
  • cJSON — im Quellbaum enthalten (cJSON.c + cJSON.h), wird direkt mitkompiliert; keine externe Library nötig
  • Stack: mindestens 32 KB (AmiSSL benötigt mehr als reines bsdsocket)
  • RAM: Programm < 100 KB, AmiSSL-Library shared aus LIBS:

HTTPS-Implementierung: bsdsocket + AmiSSL

/* Ablauf eines HTTPS-Requests auf dem Amiga */

/* 1. Libraries öffnen */
SocketBase = OpenLibrary("bsdsocket.library", 4);
AmiSSLMasterBase = OpenLibrary("amisslmaster.library", AMISSLMASTER_MIN_VERSION);
InitAmiSSL(...);  // öffnet intern amissl_v5xx.library (AmiSSL 5.27 / OpenSSL 3.x)

/* 2. TCP-Socket + Verbindung (identisch zu reinem HTTP) */
sock = socket(AF_INET, SOCK_STREAM, 0);
/* gethostbyname + connect auf Port 443 ... */
connect(sock, (struct sockaddr*)&addr, sizeof(addr));

/* 3. TLS-Handshake über AmiSSL (OpenSSL-API) */
ctx = SSL_CTX_new(TLS_client_method());
SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER, NULL);   // Zertifikat prüfen!
SSL_CTX_set_default_verify_paths(ctx);            // AmiSSL CA-Bundle nutzen
ssl = SSL_new(ctx);
SSL_set_fd(ssl, sock);
SSL_connect(ssl);                                 // TLS-Handshake

/* 4. HTTP-Request senden — identisch zu HTTP, nur SSL_write statt send */
snprintf(req, sizeof(req),
    "GET /amicloud/api.php?action=list&path=/ HTTP/1.0\r\n"
    "Host: srv.example.com\r\n"
    "Authorization: Basic dXNlcjpwYXNz\r\n"
    "Connection: close\r\n"
    "\r\n");
SSL_write(ssl, req, strlen(req));

/* 5. Response lesen via SSL_read statt recv */
while ((n = SSL_read(ssl, buf, sizeof(buf))) > 0) { /* sammeln */ }

/* 6. Aufräumen */
SSL_shutdown(ssl);  SSL_free(ssl);  SSL_CTX_free(ctx);
CloseSocket(sock);
CleanupAmiSSL(...);
CloseLibrary(AmiSSLBase);
CloseLibrary(SocketBase);
Die gesamte HTTP-Request-Logik (Header, URL, Methode) ist identisch zu HTTP — nur send/recv wird durch SSL_write/SSL_read ersetzt. Das ist exakt die Trennlinie in http_amiga.c.

Amiga-Besonderheiten

  • Libraries explizit öffnen/schließen (OpenLibrary/CloseLibrary).
  • Amiga-Pfade (DH0:, RAM:) direkt an fopen() — AmigaOS versteht diese nativ.
  • Config: ENV:amicloud.cfg (Amiga-Konvention), Fallback: Programmverzeichnis.
  • Stack per Stack 32768-Befehl setzen oder in der Binary fixieren.
  • 68000-kompatibel compilieren: kein FPU-Code, kein 68020+-Inline in geteilten Dateien.

9 — AmigaOS Filesystem-Handler (CLOUD:-Device)

AmigaOS 3.x C Erweiterte Komponente

Der Filesystem-Handler ermöglicht es, den AmiCloud-Speicher als normales Amiga-Laufwerk einzubinden (nur AmiCloud-REST — für OwnCloud gibt es stattdessen das eigenständige AmiCloudSync-Commodity, siehe docs/user/AmiCloudSync-Handbuch.html): 

; Nach dem Mounten:
DIR CLOUD:
COPY CLOUD:dokumente/readme.txt RAM:
COPY DH0:bericht.txt CLOUD:dokumente/bericht.txt

Jedes normale Amiga-Programm kann dann auf die Cloud-Dateien zugreifen, ohne den AmiCloud-CLI-Client zu kennen.

Konzept: AmigaOS DOSHandler

Ein DOSHandler ist ein spezieller AmigaOS-Prozess, der DosPackets von dos.library empfängt und bearbeitet. Er verhält sich wie ein Treiber: wenn ein Programm Open("CLOUD:file", MODE_OLDFILE) aufruft, leitet AmigaOS einen entsprechenden DosPacket an den Handler weiter.

Relevante DosPacket-Typen

Paket-TypAmigaOS-AktionAmiCloud-Übersetzung
ACTION_LOCATE_OBJECT Lock() — Datei/Ordner öffnen info-API-Call zum Prüfen ob Pfad existiert
ACTION_FREE_LOCK UnLock() Lokalen Lock-State freigeben
ACTION_EXAMINE_OBJECT Examine() — FileInfoBlock füllen info-API-Call → FileInfoBlock
ACTION_EXAMINE_NEXT ExNext() — nächster Verzeichniseintrag Gecachte list-Antwort iterieren
ACTION_FIND_INPUT Open(..., MODE_OLDFILE) Download-URL vormerken; Daten lazy nachladen
ACTION_FIND_OUTPUT Open(..., MODE_NEWFILE) Puffer anlegen, beim ACTION_END als Upload senden
ACTION_READ Read() Chunked Download via download?offset=N&length=M
ACTION_WRITE Write() In lokalen Puffer schreiben
ACTION_END Close() Bei Write-Mode: Puffer via upload-API senden
ACTION_SEEK Seek() Offset-Variable aktualisieren (nächstes ACTION_READ nutzt neuen Offset)
ACTION_DELETE_OBJECT DeleteFile() delete-API-Call
ACTION_CREATE_DIR CreateDir() mkdir-API-Call
ACTION_DISK_INFO Info() Feste Werte zurückgeben (oder zukünftig Quota-API)

Lese-Strategie: Lazy Streaming mit Offset-Downloads

Das Herunterladen großer Dateien in einem Stück in den Amiga-RAM wäre problematisch. Daher: Der Handler lädt in Chunks der Größe z.B. 4–8 KB herunter, jeweils via download?offset=N&length=M. Das macht den ACTION_SEEK ebenfalls effizient.

Schreib-Strategie: Write-Through-Puffer

Beim Schreiben puffert der Handler alle ACTION_WRITE-Daten im Amiga-RAM. Beim ACTION_END (Close) wird der komplette Puffer als ein einziger HTTPS-POST hochgeladen. Dateigröße ist durch verfügbaren RAM begrenzt — für Amiga-typische Dateigrößen aber kein Problem.

MountList-Eintrag

/* DEVS:DOSDrivers/CLOUD oder S:startup-sequence: */
Mount CLOUD: FROM S:AmiCloud.mount

/* S:AmiCloud.mount: */
CLOUD:
    Handler      = L:AmiCloud-Handler
    StackSize    = 32768
    Priority     = 5
    GlobVec      = -1
    Startup      = "https://srv.example.com/amicloud|bob|s3cr3t"
    /* Startup-String: URL|user|pass, geparst vom Handler beim Start */
Alternativ kann die Konfiguration aus ENV:amicloud.cfg gelesen werden, um das Passwort nicht im MountList-Eintrag im Klartext zu haben.
Nachtrag: Ein WebDAV-Backend im Filesystem-Handler (per BACKEND_WEBDAV/expat.library, wie hier ursprünglich geplant) wurde nie gebaut. Stattdessen entstand OwnCloud- Anbindung als eigenständiges Projekt: AmiCloudSync, ein separates Commodity (kein Handler/Laufwerk) mit einem schlanken, selbstgeschriebenen WebDAV-Client (kein expat.library — ein kleiner Tag-Scanner statt eines vollen XML-Parsers, siehe core/libcloudsync/src/webdav.c). Details: docs/user/AmiCloudSync-Handbuch.html.

Entwicklungsreihenfolge Handler

  1. Minimaler DOSHandler-Rahmen (Message-Port, Paket-Loop, Startup)
  2. ACTION_EXAMINE_OBJECT + ACTION_EXAMINE_NEXT (DIR CLOUD: funktioniert)
  3. ACTION_FIND_INPUT + ACTION_READ + ACTION_END (Dateien lesen)
  4. ACTION_FIND_OUTPUT + ACTION_WRITE + ACTION_END (Dateien schreiben)
  5. ACTION_DELETE_OBJECT, ACTION_CREATE_DIR
  6. ACTION_SEEK + Chunk-Download

10 — Webinterface (Browser)

PHP 7.4

Das Webinterface ist ein schlankes Browser-Frontend direkt auf dem Server — kein JavaScript-Framework, kein Build-Step. Eine einzelne PHP-Datei (web.php) übernimmt Login, Verzeichnisnavigation, Upload, Download und Löschen.

web.php nutzt dieselben includes/ wie api.php (DB, FileStore) — kein doppelter Code. Anstelle von HTTP Basic Auth wird eine PHP-Session verwendet.

Neue Dateien

/var/www/amicloud/
    api.php          ← unverändert (CLI-Clients, Amiga)
    web.php          ← NEU: Webinterface (Login + Dateibrowser)
    web.css          ← NEU: Styling
    includes/        ← unverändert

Ablauf

Login

  • GET /web.php → Loginformular (wenn keine Session)
  • POST /web.php → Credentials gegen DB prüfen
  • Bei Erfolg: session_regenerate_id(true), $_SESSION['user'] setzen, Redirect
  • Bei Fehler: Formular mit Fehlermeldung
  • ?logout → Session zerstören, Redirect zum Login

Dateibrowser

  • GET /web.php?path=/sub → Verzeichnisinhalt
  • Breadcrumb-Navigation (klickbare Pfadanteile)
  • Ordner → Link zu web.php?path=/sub/ordner
  • Datei → Download-Link + Löschen-Button
  • Upload-Formular (multipart/form-data)

FileStore anpassen

Die bestehenden FileStore-Methoden schreiben JSON direkt in die Ausgabe (für api.php). Für das Webinterface werden interne Varianten benötigt, die Daten als Array zurückgeben: 

// bisherig (api.php):
FileStore::list($path)           // gibt JSON aus & exit

// neu (web.php):
FileStore::listRaw($path, $uid)  // gibt array zurück
FileStore::uploadRaw($path, $uid, $tmpFile)
FileStore::deleteRaw($path, $uid)

Die bestehenden JSON-Methoden rufen intern die *Raw-Varianten auf — reine Refaktorisierung ohne Verhaltensänderung.

Grundstruktur web.php

<?php
session_start();
define('AMICLOUD', 1);
require __DIR__ . '/config.php';
require __DIR__ . '/includes/DB.php';
require __DIR__ . '/includes/FileStore.php';

/* HTTPS erzwingen */
if (empty($_SERVER['HTTPS']) || $_SERVER['HTTPS'] === 'off') {
    header('Location: https://' . $_SERVER['HTTP_HOST'] . $_SERVER['REQUEST_URI']);
    exit;
}

/* Logout */
if (isset($_GET['logout'])) { session_destroy(); header('Location: /web.php'); exit; }

/* Login-POST */
if ($_SERVER['REQUEST_METHOD'] === 'POST' && isset($_POST['username'])) {
    if (!hash_equals($_SESSION['csrf'] ?? '', $_POST['csrf'] ?? '')) die('CSRF');
    $user = DB::findUser(trim($_POST['username']));
    if ($user && password_verify($_POST['password'], $user['pass_hash'])) {
        session_regenerate_id(true);
        $_SESSION['user']    = $user['username'];
        $_SESSION['user_id'] = (int)$user['id'];
        header('Location: /web.php'); exit;
    }
    $loginError = 'Ungültige Zugangsdaten';
}

/* Session prüfen */
if (empty($_SESSION['user'])) {
    $_SESSION['csrf'] = bin2hex(random_bytes(16));
    /* Login-HTML ausgeben */
    exit;
}

/* Upload */
if ($_SERVER['REQUEST_METHOD'] === 'POST' && isset($_FILES['file'])) {
    if (!hash_equals($_SESSION['csrf'], $_POST['csrf'] ?? '')) die('CSRF');
    $dest = sanitizePath(($_GET['path'] ?? '/') . '/' . basename($_FILES['file']['name']));
    FileStore::uploadRaw($dest, $_SESSION['user_id'], $_FILES['file']['tmp_name']);
    header('Location: /web.php?path=' . urlencode($_GET['path'] ?? '/')); exit;
}

/* Löschen */
if (isset($_GET['delete'])) {
    FileStore::deleteRaw(sanitizePath($_GET['delete']), $_SESSION['user_id']);
    header('Location: /web.php?path=' . urlencode($_GET['path'] ?? '/')); exit;
}

/* Verzeichnislisting */
$currentPath = sanitizePath($_GET['path'] ?? '/');
$entries     = FileStore::listRaw($currentPath, $_SESSION['user_id']);
/* HTML ausgeben */

Sicherheit

  • HTTPS erzwungen (Redirect, damit der Browser folgt)
  • PHP-Session mit session_regenerate_id(true) nach Login
  • CSRF-Token in allen Formularen
  • Upload: nur basename() des Dateinamens — kein Path Traversal
  • Alle Pfade durch sanitizePath()
  • Download via readfile() mit Content-Disposition-Header — keine direkte URL zu Dateien im Storage

Deployment

web.php und web.css einfach in /var/www/amicloud/ kopieren — kein Apache-Neustart, kein neues Zertifikat, keine Config-Änderung.

14 — OwnCloud auf demselben Server — Verhältnis zu AmiCloud

OwnCloud läuft auf demselben Alma Linux 9.8-Server, aber getrennt: eigener Apache-VirtualHost, eigenes Verzeichnis (/var/www/owncloud/), eigenes Let's Encrypt-Zertifikat. AmiCloud kommt als Unterordner der eigenen Webseite (/var/www/html/amicloud/) — die beiden Systeme haben keinen gemeinsamen DocumentRoot.

  • Server-Deployment: AmiCloud unter /var/www/html/amicloud/ (Unterordner der eigenen Webseite) — kein neuer vHost, keine Apache-Änderungen.
  • Filesystem-Handler: spricht ausschließlich AmiCloud-REST — kein WebDAV-Backend darin (s. Abschnitt 9).

AmiCloud eigenständig (umgesetzt)

  • Einfaches JSON-REST-API statt WebDAV+XML
  • Eigene MariaDB-Tabellen (keine Abhängigkeit von OwnCloud-Interna)
  • Unabhängig von OwnCloud-Versionen und -Updates
  • Eigene Benutzerverwaltung
  • Kein Risiko für bestehende OwnCloud-Daten

OwnCloud-Anbindung (umgesetzt, aber anders als hier geplant)

  • Kein Handler-Backend, kein expat.library-XML-Parser — stattdessen ein eigenständiges Commodity (AmiCloudSync), das per WebDAV mit einem separaten OwnCloud/Nextcloud-Server abgleicht
  • Eigener kleiner Multistatus-Tag-Scanner statt einer vollen XML-Bibliothek (RAM-schonender auf dem 4-MB-Ziel) — siehe core/libcloudsync/src/webdav.c
  • Keine gemeinsame Dateisicht mit AmiCloud, kein gemeinsamer Speicher — zwei komplett getrennte Schienen, die nur einen Teil der C-Bibliotheken teilen (siehe docs/user/AmiCloudSync-Handbuch.html)
Fazit (aktualisiert): AmiCloud blieb eigenständig, wie hier empfohlen. Die OwnCloud-Anbindung kam nicht als Backend-Option im Filesystem-Handler (der hier diskutierte BACKEND_WEBDAV/ expat.library-Ansatz wurde nie gebaut), sondern als eigenes Projekt: AmiCloudSync, ein separates Sync-Commodity mit eigenem, schlankem WebDAV-Client. OwnCloud und AmiCloud koexistieren weiterhin auf demselben Server ohne Berührungspunkte — jetzt zusätzlich ohne gemeinsamen Client-Code für den WebDAV-Teil.
